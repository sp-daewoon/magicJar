# magicjar-direction-guard

이 스킬의 목적은 변경을 늦추는 것이 아니라, 이미 쌓인 구조를 모른 채 방향을 꺾는 일을 막는 것이다. magicJar는 자동매매·KIS 시세·전략 평가·화면 UX가 맞물린 시스템이므로, 코드 변경은 항상 "전과 후"를 같이 본다.

## 적용 시점

- 리팩터링, 모듈 경계 변경, 데이터 모델/API 계약 변경
- 캔들 수집·집계·차트·FVG·오더블록·스크리너·자동매매 흐름 변경
- 사용자 화면, 사이트 UX, 상태 표시, 에러 처리 변경
- 기존 정책과 다른 외부 API·스케줄·데이터 소스·운영 방식 제안
- 버그 수정처럼 보여도 흐름이나 정책을 바꿀 수 있는 작업

## 작업 전 체크

1. 먼저 현재 권위를 읽는다: `CLAUDE.md`, `_workspace/INDEX.md`, `docs/architecture/policies/`, 관련 ADR/spec/backlog, 그리고 실제 코드.
2. 기존 방향을 한 문단으로 요약한다: 현재 구조가 어떤 문제를 풀고, 어떤 제약을 받아들이는지 적는다.
3. 변경 후 방향을 비교한다: 데이터 흐름, 자본 흐름, API 계약, DB/Redis/Kafka 키, 운영 스케줄, 화면 UX, 테스트 범위가 어떻게 달라지는지 본다.
4. 사이트 이슈를 확인한다: 화면 상태 문구, 빈 데이터, 로딩/준비 중, 모바일/데스크톱 레이아웃, 사용자 오해 가능성을 같이 점검한다.
5. 기존 방향을 틀면 작은 패치로 처리하지 않는다: 대안, 리스크, 마이그레이션, 롤백, 사용자 확인 필요 여부를 남긴다.

## 판단 원칙

- 기본값은 보수적 보강이다. 기존 구조를 살리면서 누락된 경로를 채우는 쪽을 먼저 검토한다.
- mock·임의 합성 데이터로 빈틈을 덮지 않는다. 데이터가 없으면 "없음/준비 중/백필 대기"로 표현한다.
- 방향 전환이 필요하면 코드보다 먼저 결정 기록을 정리한다. ADR/spec 갱신 없이 정책을 바꾸지 않는다.
- 프론트 변경은 기능뿐 아니라 사용자가 무엇을 믿게 되는지까지 본다.
- 자동매매·주문·계좌·KIS 호출량에 닿는 변경은 운영 리스크와 롤백 경로를 반드시 확인한다.

## 응답/작업 형식

작업을 시작할 때 짧게 남긴다:

```text
기존 방향: ...
변경 의도: ...
방향성 영향: 유지 / 부분 변경 / 전환
확인할 리스크: 데이터, 자본 흐름, API, UX, 운영, 검증
```

구현 후에는 실제로 확인한 검증과 남은 리스크를 말한다.
