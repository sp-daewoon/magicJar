① 인과 — 왜 이 작업을 했나

  • 감사 §0 결론: "데이터가 오염돼 못 한 게 아니라, 캔들 단일 진실원을 못 확보한 채 기능을 얹어 최종값이 실행 순서에 의존. 오염은 증상." 진실원 6단·writer 8경로·DO NOTHING/UPDATE 혼재.
  • 사용자 방향: 전종목 관리가 오염 갱신·TPS·계산량을 키운다 → 관리 대상을 대·중형으로 좁히고, 필요한 소형주는 온디맨드로만 편입.
  • DailyCloseFinalizer가 insertIgnore(DO NOTHING)로 공식 마감가(priority 1)를 쓰던 역전 결함도 확인(진행값이 확정가를 못 덮게 되려 반대로 작동).

④ 완주 자동화 — cap 절대값 종료의 3대 공백 보강

사용자 지적: "6000콜 절대값에서 자르고 마는 건, 완주 보장·실패 알람 오퍼레이션이 없으면 정합성 서비스가 아니다." → MarketDailyBackfillAutoRunner(@Scheduled 5분)로 보강.

  • 자동 재시도 트리거 — CAP_REACHED 시 다음 tick이 자동 이어받기 (사람 run 반복 불필요)
  • 완주 판정 — remaining=0/COMPLETED → SystemEventCategory.MARKET_DATA INFO emit + idle
  • 정체 알람 — 3회 연속 진행 0 → WARN emit + 자동 재시도 중단(KIS 무한 타격 방지), /system 가시화, resumeAfterStall() 수동 재개
  • 실증: 23:51 첫 tick에서 status=COMPLETED remaining=0 — 남은 2종목(KIS 일시 status=500)까지 자동 완주.

⑤ 성능 — backfill 병목 진단·해소

  • 초기 배치 12종목·실패 67%. 원인: KIS 일봉 endpoint 100건/호출 페이지네이션 × BG버킷 초당 2토큰 + 버킷 합 불일치(12≠capacity10 → 단일버킷 fallback) → acquire timeout(우리 rate-limiter 자체 실패, KIS 아님).
  • 해소: 매매 트래픽 0 구간에 env BG8 + concurrency8 + capacity16(합 정합) + acquire timeout 5s→60s(경합 시 실패 대신 대기, gap 원천 차단).
  • 효과: 배치당 12 → 225~270종목, 실패율 67% → <1%. env는 미커밋(운영 튜닝), 완주 후 원복 예정.
