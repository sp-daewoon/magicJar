운영 기준

신규 Redis 키는 기본적으로 domain/src/main/kotlin/kr/spdaewoon/magicjar/domain/redis/RedisKeyRegistry.kt에 등록해야 합니다. 예외는 Bucket4j처럼 라이브러리가 내부 상태를 관리하거나, 주문 멱등성처럼 caller의 비즈니스 키를 그대로 감싸는 경우입니다.

1. Registry-first

런타임 키 문자열은 Registry에서 생성합니다. 코드 주석에 구형 키가 남아 있어도 실제 기준은 Registry입니다.

2. 라벨 명명

user:, code:, interval:처럼 차원을 명시해 운영자가 한눈에 읽게 합니다.

3. TTL 필수

캐시·락·dedupe·rate-limit 키는 누수 방지를 위해 TTL 또는 명시 삭제 경로를 가져야 합니다.

4. 주문 훅 우선

계좌/포지션 관련 캐시는 주문 접수·거부·취소·체결·WS 불확실 상태에서 무효화 또는 refresh가 필요합니다.

삭제 판단

장중에는 kis:oauth:token, account:balance, market:candle, kis-rate-limit 계열을 수동 삭제하지 않는 것이 안전합니다. 삭제하면 KIS 재발급·잔고 재조회·캔들 재시드가 즉시 발생할 수 있습니다.

장 종료 후 전체 Redis 초기화가 필요하면 앱을 내리고 삭제한 뒤 재기동하는 쪽이 가장 예측 가능합니다. 앱이 살아 있는 상태에서 삭제하면 일부 키는 즉시 재생성됩니다.

idem:order:{idempotencyKey} OrderRouterKafkaListener + OrderIdempotencyGuardImpl 자동/수동 주문 중복 제출 방지 60s SETNX caller가 만든 비즈니스 idempotencyKey를 그대로 감쌉니다. 자동 청산은 auto-tp:, auto-sl:, auto-vi:, auto-tpt: digest를 사용합니다. Registry에 Order.idempotency(key)를 추가하는 후속 중앙화 권장. 삭제 시 60초 내 중복 주문 방어가 풀립니다.

주요 흐름

계좌 잔고 singleflight

API와 consumer가 같은 account:balance:user:{userId}:account:{accountType}를 봅니다. cache miss 시 :lock SETNX로 KIS 잔고조회 1회만 수행하고, 나머지는 캐시 결과를 공유합니다.

주문 이벤트 정합

주문 접수·거부·취소·체결·WS 누락 의심은 계좌 캐시를 dirty 처리해야 합니다. 삭제 자체보다 “다음 거래 판단 전 refresh”가 핵심입니다.

실시간 구독 관측

consumer가 ops:realtime:status를 5초 주기로 쓰고 API가 15초 초과 stale을 장애로 봅니다. 이 키가 만료되면 관리자 화면의 빨간 상태가 정상적으로 켜집니다.

레거시 키 정리 상태

scripts/ops/2026-06-15-delete-legacy-redis-keys.sh dry-run 결과: legacy redis key candidates: 0.

스크립트는 access_token:*, kis:token:*, account:balance:*, position:current:*, quote:last:*, candle:current:*, candle:today:*, strategy:active:by_code:*, perf:*, watchlist:source:*, reconcile:* 등 구형 패턴만 대상으로 합니다. 표준 키와 충돌 가능한 일부 패턴은 skip guard를 둔 상태입니다.

남은 정리 권장

  • 주석에 남은 구형 키명(position:current, quote:last, perf:, session:cache 등)을 실제 Registry 키명으로 갱신합니다.
  • idem:order:{idempotencyKey}는 후속 PR에서 Registry helper로 중앙화하면 grep/운영 문서가 더 깔끔해집니다.
  • Bucket4j kis-rate-limit:global은 직접 Registry 생성 대상은 아니지만, 설정 key prefix를 상수화해 API/consumer/batch drift를 막는 것이 좋습니다.
  • Redis 전체 삭제가 필요할 때는 장 종료 후 앱 컨테이너를 먼저 내리고 Redis를 비운 뒤 앱을 올리는 절차를 runbook으로 고정하는 편이 안전합니다.
