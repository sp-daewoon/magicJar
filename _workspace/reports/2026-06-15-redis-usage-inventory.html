전체 사용 구조

Redis는 단순 캐시만이 아니라 KIS 인증 토큰, rate limit bucket, account snapshot singleflight, 실시간 quote/candle write-through, 주문 idempotency, 리스크 빈도 제한, dedup, 운영 상태 스냅샷까지 담당한다. 그래서 이름 정리는 “보기 좋게 바꾸기”가 아니라 장애 대응 시 어떤 키를 봐야 하는지 바로 찾게 만드는 작업으로 접근해야 한다.

즉시 눈에 띈 이상 징후

quote:last:* TTL 불일치. 코드상 quote cache는 5분 TTL 성격인데 라이브 샘플에서 일부 종목 TTL이 70,000초에서 242,000초대로 관측됐다. 일부 키는 정상 300초였다. 과거 writer 잔재 또는 다른 writer가 긴 TTL로 저장하는 경로가 남아 있을 가능성이 높다.

  • 현재 실시간/차트 증상과 직접 연결될 수 있어 quote:last writer 전수 점검이 1순위다.
  • 뉴스 dedup이 2,268개로 대부분이지만 TTL성 dedup이라 메모리 위험은 낮다.
  • 운영 계좌 키는 소수지만 삭제/rename의 영향이 크므로 배포 중 wire 변경은 피해야 한다.

권장 Naming Convention

기존 Redis 키는 prefix가 기능별로 제각각이다. 신규/개편 키는 아래 규칙을 기준으로 맞추고, 기존 운영 키는 위험도별로 “문서화만”, “dual-read/write”, “장 마감 후 cutover”로 분리하는 것을 권장한다.

기본형 {domain}:{resource}:{purpose}:{dimensions}

Redis 자체가 저장소이므로 모든 키에 redis:를 붙이지는 않는다. 대신 domain을 명확히 둔다.

Dimension 순서 user:{userId}:account:{REAL|MOCK}:code:{code}:interval:{interval}

사용자 스코프 키는 user를 먼저 둔다. 종목/전략/날짜/윈도우는 명시 label을 붙인다.

Lock/Dedup/Rate limit ...:lock, ...:dedup, ...:bucket

상태와 목적이 root prefix로 흩어지지 않게 같은 domain 아래 둔다.

선택지로 mj: namespace를 앞에 붙이는 방법도 있다. 다만 현재 DB가 단일 서비스 전용이면 mj:보다 domain 정렬이 더 실용적이다. 다른 서비스와 Redis를 공유하게 되면 mj:{domain}:...로 확장한다.

KIS / Auth

토큰, approval key, key changed lock, global rate limit.

  • kis:token, kis:approval
  • kis-rate-limit:global:*
  • 장애 시 외부 API 폭주와 직결

Account / Order / Risk

계좌 snapshot singleflight, 주문 idempotency, 일/분 거래 빈도 제한.

  • account:balance, account:availability
  • risk:trade-freq, idem:order
  • rename보다 정합성 hook이 우선

Market / Candle

실시간 quote, orderbook top, live candle, backfill guard.

  • quote:last, orderbook:top
  • candle:current, candle:today
  • TTL/interval 표준화 필요

Strategy / Analysis

전략 active cache, signal dedupe, indicator/pattern/AI prompt cache.

  • strategy:active, signal:dedupe
  • indicator:cache, pattern:cache
  • hash segment 의미 명확화 필요

Ops / Discovery

뉴스/공시 dedup, realtime status, source tracker, instrument sync.

  • admin:realtime-status
  • news:dedup, instrument:sync
  • 운영 조회용 prefix 정돈 여지 큼

Migration Proposal

Inventory & Registry

wire key 변경 없이 Redis key registry를 만든다. 공유 키는 공통 registry, 모듈 내부 전용 키는 owner 패키지에 object로 고정한다.

대상: account, KIS, quote, candle, ops status.

Low-risk Alias

indicator, pattern, perf, meta, screener처럼 재계산 가능한 캐시부터 v2 write + v1 fallback read를 적용한다.

원칙: TTL 만료로 v1 자연 소멸.

Critical Dual-run

account/order/risk/KIS는 장 마감, in-flight 주문 0, WS 안정 상태에서만 dual-read를 검토한다.

금지: 장중 idempotency/risk key rename.

Cutover & Cleanup

운영 대시보드가 v2 key를 읽고, dozzle/metric 알림도 v2 기준으로 바뀐 뒤 v1 cleanup을 진행한다.

검증: key count, TTL, stale ratio, KIS call count.

우선순위 추천안

  1. quote:last:* TTL anomaly 먼저 제거. 모든 writer를 찾아 TTL 300초가 아닌 경로를 차단하고, stale quote가 매매/화면에 들어가지 않게 age check를 강화한다.
  2. RedisKeyRegistry 도입. account/KIS/market/ops 공유 키부터 문자열 literal을 상수 함수로 모으고, 테스트에서 key pattern을 고정한다.
  3. 계좌 snapshot 계열은 rename보다 hook 정합성. 주문 접수, 거부, 취소, 부분/전체 체결, 수동 체결 감지, WS 불확실 상태의 invalidate/refresh 규칙을 registry와 함께 문서화한다.
  4. order/risk key는 정책 이름까지 포함. 일별 최대 거래가 “주문 시도 수”인지 “매수 체결 수”인지 “왕복 거래 수”인지 key/report/config에 드러나야 한다.
  5. market key는 market: 아래로 모으기. quote, orderbook, meta, session, candle을 같은 도메인으로 묶으면 장애 시 Redis scan이 쉬워진다.
  6. 저위험 캐시부터 v2 naming 전환. indicator, pattern, perf, screener, AI prompt는 재생성 가능하므로 가장 먼저 이름 정리 실험을 하기 좋다.

비교적 안전

재계산 가능한 조회 캐시. 삭제 시 성능 저하 또는 일시 miss 정도가 주 영향이다.

  • indicator:cache:*, pattern:cache:*
  • screener:cache:*, perf:*
  • meta:*, 단 quote TTL 정상 확인 후

주의 필요

삭제가 외부 호출 증가나 화면 상태 흔들림으로 이어질 수 있다.

  • kis:token:*, kis:approval:*
  • account:balance:*, quote:last:*
  • admin:realtime-status, watchlist:source:*

장중 삭제 금지

중복 주문, 리스크 우회, 복구 폭주를 만들 수 있다.

  • idem:order:*, auto-*
  • risk:trade-freq:*
  • account:availability:* projection 적용 후
  • candle:backfill:guard:* 대량 삭제
