1부 — 처음 접하는 개발자를 위한 시스템 설명이 시스템이 무엇이고, 어떻게 구성되며, 어떻게 돌리는가

1.1 magicJar는 무엇인가

magicJar(마법의항아리)는 룰 기반 quant trading 시스템이다. 종목 마스터 + 기술적 지표 + 전략 DSL + 시그널이 자동 주문까지 이어지는 것이 본체다. 영속 데이터 기반 분석·스크리너·백테스트는 AI·외부 LLM·인터넷 단절과 무관하게 재현 가능하지만, 실시간 시세·잔고·자동 주문은 KIS REST/WS 연결이 필수다. AI(Claude·Gemini·OpenAI)는 사용자가 버튼을 눌렀을 때만 호출되는 옵션 분석 보조로, 종목 코멘트·기업 분석·차트 해석·지표 의미 설명을 제공할 뿐 매매 트리거·결정권은 0이다. 매매 결정은 오직 DSL 룰 평가 결과로만 발생한다. 미래에는 magicJar가 MCP 서버를 노출해 Claude·Cursor 같은 외부 AI 클라이언트가 magicJar의 도메인을 호출하도록 한다(우리가 server, AI가 client).

사용자 정정 원문(2026-05-02) — "AI가 매매를 하는건 허용하는게 아니다. 신호에 의한이고 AI는 옵션이다 … AI가 메인이 되면 안됨!!" 이 한 줄이 전체 아키텍처의 최상위 제약이다.

1.2 기술 스택

백엔드 (JVM)

  • Kotlin 2.0 (K2 컴파일러) + JDK 21
  • Spring Boot 3.3 + Spring AI
  • Gradle KTS (호스트 wrapper 빌드)
  • PostgreSQL 16 (Flyway 마이그레이션)
  • Redis 7 (캐시·시세·분산락)

프론트엔드 (SPA)

  • React 19 + TypeScript + Vite
  • Tailwind CSS
  • LWC v4 (TradingView Lightweight Charts)
  • pnpm 패키지 매니저
  • REST + STOMP(WebSocket) 실시간 구독

외부 연동: KIS OpenAPI(REST + WebSocket, 조회 credential과 주문 credential 분리) · DART 공시 · Naver Open API 뉴스 · LLM 공급자(옵션). 빌드 도구는 호스트 Gradle wrapper이며 package.json은 husky 호스트 + 상태 스크립트 전용이다(앱 코드와 무관).

1.4 데이터 흐름 — A → B → C → D

데이터는 4영역 19컴포넌트를 지난다. 데이터 수집·정합(A) → 분석·전략(B) → 의사결정·실행(C) → 학습·운영·UI(D). 아래 흐름 전체가 AI 호출 0건이며 외부 LLM이 끊겨도 정상 동작한다.

그림 2 — 4영역 데이터 흐름 (source: docs/architecture/diagrams/onboarding-data-flow.drawio)

본체 자동매매 사이클(master §3-1)의 실제 단계

  1. [0] Position Bootstrap — consumer 부팅 시 KIS 잔고(TTTC8434R)를 DB position에 upsert + Redis 워밍 + KIS WS 구독 시작.
  2. [1~2] InstrumentSyncJob(17:00) → DailyCandleBackfillJob(18:00) + CorpActionSyncJob(18:30).
  3. [3] Screener — 사용자 트리거 시 universe × DSL → 후보 + 4기준 랭킹(inline 동기 평가).
  4. [4] SignalEngine — KIS WS tick → 분봉 합성 → DSL 평가 → BUY/SELL/HOLD.
  5. [5] Risk Guard chain(6단) — KillSwitch·Session·DailyLimit·PositionLimit·Drawdown·PriceSanity.
  6. [6~7] KisOrderSender → KIS API → 체결통보(WS) → order_execution → position 갱신.
  7. [8~9] Trading Journal 자동 기록 → 일별 PerformanceJob(P&L·MDD·승률).

1.5 실시간 시세 아키텍처 — KIS WS owner 4종

KIS WebSocket은 40 slot 한도가 있고, 이 예산을 owner priority로 배분한다. 핵심 방향 가드는 매매 경로(STRATEGY)가 관찰 경로(DETAIL)보다 우선이라는 점이다. watchlist는 WS를 쓰지 않는다(ADR 0124). polling 전용 경계는 유지하지만 현재 WatchlistPollingWorker는 KIS 호출이 제거된 no-op이므로 자동 5초 시세 공급이 존재한다고 해석하면 안 된다. 체결가는 H0UNCNT0 단일 통합 채널(KRX+NXT·종목당 1채널)로 받는다.

그림 3 — KIS WS owner priority (source: docs/architecture/diagrams/onboarding-ws-owner-priority.drawio)
실무 함정 — "WS 30초 단절 → 전 종목 5초 polling" 폴백은 존재하지 않는다(2026-07-03 감사 정정). WatchlistPollingWorker는 KIS 호출이 제거된 no-op stub이며, WS 단절 시 실재하는 degraded 경로는 ACTIVE 전략 명시 종목 한정 degraded polling뿐이다. HOLDING·PENDING_BUY는 evict 절대 금지다.

1.6 안전 장치

실계좌 이중(실질 3중) 게이트

실주문이 나가려면 환경변수 두 개가 모두 참이어야 한다.

MAGICJAR_MODE=REAL MAGICJAR_ALLOW_REAL=true

여기에 주문 실행 트랙(T-O)은 user_account.real_trading_consent_at 사용자 동의까지 더한 3중 게이트를 적용한다. dev/staging은 항상 MOCK이다.

Guard chain 6단 + KillSwitch

시그널이 주문이 되기 전 6단 룰(KillSwitch·MarketSession·DailyLimit·PositionLimit·DrawdownStop·PriceSanity)을 short-circuit 통과해야 한다.

KillSwitch ON 시 시그널 emit 정지 + pending 취소 + 신규 주문 422 + STOMP push. 잔고 reconcile drift 감지 시 KillSwitch가 auto-ON 된다.

  • Reconcile — 시장 OPEN 5분/CLOSED 1시간 cron으로 KIS 실잔고 vs DB position을 대조, drift 시 KillSwitch auto-ON.
  • Ledger rebuild(ADR 0115) — 보유 수량 같은 파생 원장은 immutable 진실원 order_execution에서 결정론적으로 재계산 가능해야 한다. drift 시 진실원에서 rebuild로 수렴(증분 누락 영구화 방지).
  • Self-heal(ADR 0136, default-off opt-in) — 명시 활성화 시 장중 10분 cron으로 KIS 실보유 ↔ strategy_position ledger를 대조, KIS 권위 주입 rebuild로 정정.
  • Canary + drain — 헌법 §9-2 dev→staging→REAL 30분 staging dwell. consumer(체결·자본 경로) 재배포는 장중 in-flight 주문 0 확인 후 또는 장 마감 후(ADR 0115 §2-P2-④).
  • 기본 profile = dev,real-kis — mock 부팅 path는 폐기됐고 mock은 JVM test fixture 전용이다.

2부 — 이 시스템은 무엇에 중점을 두는가설계 문서를 읽고 도출한 아키텍처의 무게중심

2.1 왜 룰 기반이 본체이고 AI는 보조인가

비전(§1)이 못박은 제약이다. AI가 매매 결정을 내리면 재현 불가능·감사 불가능·오프라인 불가능한 시스템이 된다. magicJar는 반대로 "마스터 데이터만으로도 종목이 추출 가능한 시스템"을 기본 목적으로 삼고, AI는 그 결과에 대한 코멘트·기업분석을 옵션으로 얹는다. 그래서 개발 룰 5번(AI 호출 자제)은 W1~W3 트랙 코드에 LLM provider import가 발견되면 리뷰 reject다. 매매 결정 토픽(ai.decision.v1)은 아예 폐기됐다.

mock 부팅 path 폐기도 같은 철학이다. 기본 profile은 dev,real-kis이고 mock은 JVM 테스트 fixture 전용이다. 운영 단계에서 사용자 흐름이 mock으로 우회되면 "실제로 동작하는 것처럼 보이지만 자본에 닿지 않는" 착시를 만들기 때문이다. 검증은 실 KIS 모의투자 서버로 한다.

2.2 자본 안전 최우선 구조

주문 경로는 이 시스템에서 가장 방어적으로 설계된 영역이다. 게이트·재검증·진실원 재계산이 겹겹이 쌓여 있다.

발주 전3중 게이트(MODE×ALLOW_REAL×사용자 동의) + Guard chain 6단 + OrderIdempotencyGuard(Redis SETNX 60초 + idempotency_key DB unique 이중 방어)
체결 후KIS WS 체결통보 → order_execution append-only 진실원 → position/strategy_position 파생 갱신

2.3 KIS API 예산 관리

KIS는 초당 호출 한도(ADR 0037 초당 10건)와 WS 40 slot 한도가 있는 공유 자원이다. 이를 넘기면 계정·앱키가 차단되어 본체 자동매매 전체가 중단되는 catastrophic risk다. 그래서 KIS REST 호출은 ADR 0116의 3-tier priority bucket(KisCallPriority — USER_PATH > REALTIME/INGESTION > BACKFILL, default-on; 비활성·설정 불일치 시 단일 global bucket으로 fail-safe 회귀)으로 라우팅하고, WS slot은 owner priority(HOLDING>PENDING_BUY>STRATEGY>DETAIL)로 배분한다. WsSlotBudgetLedger가 채널 단위로 회계하며 OPSP0008(MAX SUBSCRIBE OVER)을 선제 예방한다.

2.4 데이터 정합성 집착

  • look-ahead 차단·생존자 편향 보정 — 백테스트는 t 시점 데이터만, universe는 시점별로 상장 종목만.
  • raw + adjusted 양 컬럼 — corp action 발생 시 close_raw·close_adjusted 병존, 차트·백테스트 default는 adjusted.
  • 주문 멱등 — 주문 intent는 signal 기반 idempotency_key + Redis SETNX 60초 + order_request.idempotency_key DB unique 이중 방어로 중복 KIS 호출을 차단한다(ADR 0068 H-1, V38 현행 schema). signal_id와 kis_order_no는 현재 unique가 아니다.
  • immutable audit — 모든 order·signal·screener·AI 코멘트에 감사 row(AI 코멘트는 매매 영향 0이지만 비용·드리프트 추적).
  • 캔들 SLA·self-heal — 분봉 결측률 가드(OK≤5% / LOW_CONFIDENCE / INSUFFICIENT), mock 보간 절대 0, 부족 시 재수집 path 노출.

2.5 운영 단계 특성

magicJar는 2026-05-21(ADR 0094 amend)에 개발 종착 + 운영·점진 고도화 단계로 진입했다. 코드 한 줄 수정도 룰 본체·자본 흐름과 결합되므로 다음 문화가 자리잡았다.

  • ADR 중심 의사결정 — 외부 데이터 규격·아키텍처 결정은 ADR로 근거를 남긴다(파일명 = 헤더 번호, master §10 + README 인덱스 동시 갱신).
  • 감사·remediation 문화 — 2026-07-03 전 영역 시스템 감사(P0 1·P1 12·P2 16·P3 12)를 문서화하고, remediation tracker로 완료/구현 Wave 대상/이연을 추적한다.
  • 방향성 보존 가드 — 비트리비얼 변경 전 기존 SoT/ADR/구현을 먼저 읽고 "왜 지금 이렇게 되어 있는가"를 파악한다. 대규모 재작성보다 보수적 보강을 우선한다.
  • KIS-first raw fetch — KIS API 규격은 자체 추론 0, 공식 출처 raw fetch 인용 의무.

3부 — 향후 발전 방향로드맵 후속 Wave + 현행 이연 과제 + 구조적 개선 여지

3.1 후속 Wave의 의미

W1(watchlist+데이터)·W2(분석)·W3(자동매매 본체)는 룰 본체 풀 가동에 도달했다. 아래 W4·W5는 현재 작업 상태표가 아니라 tracks-roadmap.md의 후속 방향이며, 실제 착수·완료 상태는 _workspace/INDEX.md와 task ledger를 다시 확인한다.

후속 방향W4 — 시장 추세 + AI 옵션 + MCP

  • T-MARKET(시장 지수·섹터 추세·시장 캘린더) — Accepted, 진행.
  • T-AI(사용자 트리거 LLM 코멘트·기업 분석·AI 종목발굴 Claude CLI bridge).
  • T-MCP(MCP 서버 노출, read 전용 tool 5종 — get_candles·run_screener·get_journal·explain_indicator·backtest_strategy).

의미 — 본체가 완성됐으므로 이제 "설명·발굴 보조"와 "외부 AI가 magicJar를 도구로 쓰는" 미래를 얹는 단계. AI가 끊겨도 본체 영향 0이라는 불변식은 유지된다.

미래W5 — LWC 확장 + 학습·정합성 검증

  • T-LWC(자체 도형/주석/패턴 overlay, TradingView Advanced 의존 0).
  • T-LEARN(사용자와 함께 데이터 흐름·아키 의도·표시 의미 검증).

의미 — 시각화 고도화와 사용자 학습으로 시스템 이해를 일원화하는 마무리 Wave.

3.2 audit tracker의 현행 이연·부분 완료 과제

  • P1-④ DSL close 수정주가 vs 지표 원주가 가격 소스 정책 — 자본 흐름과 결합되므로 별도 ADR·사용자 결재 후 단일화한다.
  • P1-⑥ NEW_MKOP_CLS_CODE 세션 처리 — parser 전파는 완료됐지만 코드값별 예상체결 제외 정책은 KIS 원문·라이브 evidence 확보 전까지 부분 완료다.
  • P1-⑧ 운영 알림 실증 — Prometheus 규칙과 Alertmanager 구성은 완료됐고 실제 운영 라우팅·전송 검증이 남았다.
  • P1-⑭ KIS 자격증명 운영 조치 — 레포 밖 보관 상태를 유지하고 노출 이력이 의심되면 사용자가 예방적으로 재발급한다.
  • ADR 0139 KIS rate limiter 공유 모듈 승격 — api·consumer·batch 3중 복붙 단일화(Proposed). 구현은 전체 빌드 검증 필요로 후속 사이클 보류.
  • P2 백테스트·position 필드·공휴일·외부 API 실패 가시성·DLQ 관측 등은 tracker의 Phase 3 이연 항목으로 관리한다.

P0-1 WS 3채널 재구독, tick 0원/OHLC 가드, 프론트 STOMP 재구독, smoke 계약, alert rule 구성은 현재 tracker에서 완료로 판정됐다. 과거 감사 보고서는 당시 snapshot이며 현행 상태는 반드시 remediation tracker를 따른다.
